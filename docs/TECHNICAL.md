# immich-auto-dumper — technical documentation

How the tool works inside: what it promises, what it refuses, and what breaks if you
change it. For installing and using it, see the [user guide](GUIDE.md).

This page holds what every other technical page refers to — the principles, the pieces,
the path model and the two conventions. Start here, then follow the index at the bottom.

## Design principles

- **No privileges.** Everything runs as the invoking user — never `sudo`. Docker access
  comes from `docker` group membership; files owned by the container's user are deleted
  *through* the container.
- **Immich is the source of truth.** The tool reads Immich's database to decide what to
  do and performs one narrow write. It never "repairs" Immich: on any inconsistency it
  stops and asks the user to fix things on the Immich side.
- **Refuse rather than guess.** Every run starts with pre-flight checks. Any failure
  aborts the run before the first destructive operation.
- **An unknown is never a negative.** A dependency that cannot be reached is reported as
  unverified, never as "nothing found".
- **Resumable and undoable.** Every step is journalled before it is taken, so a run
  interrupted at any point leaves each asset either fully archived or fully intact, and one
  identified run can be undone.

## Components

```
immich-auto-dumper.sh    entry point: CLI parsing, setup wizard, status, cron start/stop
lib/utils.sh             logging, locking, prereqs, storage marker, file identity, disk
lib/config.sh            config.conf parser and validator
lib/ui.sh                interactive prompts (whiptail with plain-text fallback), gauge
lib/detect.sh            auto-detection of containers, DB credentials, mounts
lib/db.sh                every SQL statement in the project (psql via docker exec)
lib/runlog.sh            the operations journal: records, states, retention
lib/archive.sh           the archiving engine, the reconciliation and the rollback
lib/backup_db.sh         DB-dump mirroring with retention
cron/crontab.example     cron template instantiated by `start`
config.conf              generated by setup; READ, never executed (git-ignored)
```

The entry point resolves itself through the `~/.local/bin` symlink (`readlink -f`) so
`lib/`, `config.conf` and `cron/` are always found in the real install directory, whether
the tool was invoked by name, by absolute path, or from cron.

## The path model

Three coordinate systems describe the same file. Nearly every bug class in this tool's
history came from confusing two of them.

| Space | Example | Used by |
|---|---|---|
| Host, internal library | `/mnt/immich/library/library/admin/2024/06/a.jpg` | `cp`, `du`, `stat` |
| Container / DB, internal | `/data/library/admin/2024/06/a.jpg` (`IMMICH_DB_LIBRARY_PREFIX`) | `asset.originalPath` before archiving |
| Container / DB, archive | `/external_library/Alice/2024/06/a.jpg` (`ARCHIVE_CONTAINER_PATH`) | `asset.originalPath` after archiving |

Conversion is by prefix substitution, in `lib/archive.sh`:

| Function | Direction |
|---|---|
| `db_path_to_host_path()` | container/DB internal → host |
| `host_path_to_db_path()` | host → container/DB internal |
| `archive_build_dest_path()` | host internal → host archive |

`archive_build_dest_path()` preserves the full sub-path after the user folder, so any
Immich storage template layout survives unchanged. `USER_MAP` renames the per-user
top-level folder on the external storage — see
[configuration](technical/configuration.md).

### The shape guard

`archive_build_dest_path()` **refuses** — returns 1 and echoes nothing — any source that
is not of the form `<upload location>/library/<user folder>/<rest>` with both parts
non-empty. The SQL selection does not offer such an asset either, so this is a double
cover; it holds if another caller ever appears.

A malformed destination path is the one shape that matters, because of this:

### Why a stray slash is a data-loss bug

Immich stores its import paths **with a trailing slash** (`/external_library/Alice/`). A
folder taken from one and used as-is yields `Alice/`, which writes
`/external_library/Alice//2024/…` into `asset.originalPath` — while Immich's own library
scan records the single-slash form. The row and the file no longer name each other: at the
next scan the file is imported again as a **duplicate asset**, and the original row points
at a path Immich considers absent.

`_sanitize_folder()` (`immich-auto-dumper.sh`) therefore trims surrounding slashes and
collapses repeats wherever a folder name enters the tool, and `_config_check()` reports a
saved config that already carries one. Inner slashes are kept: an import path may
legitimately be nested (`family/alice`).

## The diagnostic convention

Every function that can fail to reach something answers with **three** codes, not two:

| Code | Meaning |
|---|---|
| `0` | success, the result can be used |
| `1` | a legitimate negative — absent, empty, not covered |
| `2` | no conclusion possible — dependency unreachable, permission denied, timeout |

The distinction is load-bearing, in both directions:

- **A `1` and a `2` must not lead to the same decision.** A removable disk that is simply
  unplugged is an ordinary state: the run ends quietly, exit 0. A mount that hangs or
  denies reads is a fault: the run is refused, exit non-zero. Same subject, opposite
  handling.
- **A `2` must never be reported as a `1`.** "The database did not answer" and "the schema
  has changed" produced the identical message once, which invited the operator to edit a
  tool that writes to their database while the container merely needed starting.

Two places absorb a `2` on purpose, and only those: the setup review (`_config_check()`)
and the dry-run preview. Both must open and report against a mute Immich — a user list
that cannot be read costs the display, not the screen. **Nothing on the archiving path
absorbs a `2`**; every `|| true` there is scoped to a line that only advises.

## The field separator

Multi-column results are separated by `\x01`, never by `|`, because a file path is free to
contain a `|`. A directory named `we|ird` split into three fields, bash read a truncated
parent directory and a size that was not a number, and that directory was silently never
archived.

The same separator is used in the three places that pass structured data around:
`DB_FIELD_SEP` (`lib/db.sh`), `DET_FIELD_SEP` for the Docker mount listing
(`lib/detect.sh`), and `RUNLOG_SEP` for parsed journal records (`lib/runlog.sh`).

## Database access

All SQL goes through `_db_exec()` (`lib/db.sh`), which runs `psql -t -A` inside the
Postgres container. Three details matter:

- **stdin is redirected from `/dev/null`.** `psql -c` never reads stdin, but
  `docker exec -i` keeps it open and drains it — and inside a `while read … done < <(…)`
  loop that stdin *is* the loop's input pipe, so docker would swallow the remaining rows
  and the loop would stop after one iteration.
- **A failed query returns `2`, never an empty result.** The caller must be able to tell
  "no rows" from "no database". psql's own stderr flows through to explain itself.
- **Three escaping layers**, by context: `_db_escape()` for SQL string literals,
  `_db_escape_like()` for LIKE wildcards (used with `ESCAPE '\'`), `_db_escape_regex()`
  for POSIX regex metacharacters. The wildcard and regex helpers are applied **before**
  `_db_escape()`. File names containing quotes, `%`, `_` or regex tokens are handled
  literally.

### Schema validation

`db_check_schema()` runs before any operation (via `check_prereqs()`, `lib/utils.sh`) and
verifies against `information_schema` that every column the tool relies on exists:

- `asset`: `id`, `originalPath`, `isOffline`, `isExternal`, `libraryId`, `deletedAt`,
  `ownerId`, `visibility`, `fileCreatedAt`
- `asset_exif`: `assetId`, `fileSizeInByte`
- `library`: `id`, `ownerId`, `importPaths`, `deletedAt`

One query per table, and **each must actually run**: a query that fails says nothing about
the schema, so it aborts the check with `2` rather than contribute an empty column list —
which would make every column look missing.

If an Immich upgrade renames or removes any of these, every run aborts at pre-flight with
the missing columns listed. The running Immich version (`IMMICH_SOURCE_REF` from the
image, falling back to the compose tag `IMMICH_VERSION`) is logged at the start of each
run so a failure can be tied to the upgrade that introduced it.

**Limit to be aware of:** the check verifies column *presence*. A purely additive
migration, or a semantic change with unchanged names, is not detected. Run
`immich-auto-dumper test_run` after every Immich upgrade.

### The one write

`db_update_asset_path()` is the only statement in the project that modifies Immich's
data. One `UPDATE` rewrites `originalPath` **and** the asset's library membership:

- When the new path falls under an `importPaths` entry of a library owned by the asset's
  owner, the asset is **adopted** into that library: `libraryId` set, `isExternal = true`,
  `isOffline = false`.
- When no library covers the path — which includes a rollback into the internal library —
  the asset reverts to a plain upload asset: `libraryId` NULL, `isExternal = false`.

Adoption is symmetric by construction: the same statement serves both directions, and
which way it resolves depends only on the path it is given. `DB_UPDATE_IS_EXTERNAL` carries
the resulting state (`t`/`f`) back to the caller, which refuses to complete a move that did
not adopt — see [archiving](technical/archiving.md).

The `rtrim(ip, '/') || '/%'` match accepts an import path with or without its trailing
slash, without letting `/external_library/Alice` claim `/external_library/Alice2/…`.

Nothing else in Immich's database is ever written: no album, no person, no metadata, no
setting. No Immich API key is involved.

## Tests

The pure-function test suite is **not shipped**: an end user has no use for it, and it
lives outside the repository. There is no CI — nobody runs anything for you.

`shellcheck -S warning -x` is expected to be clean on all eleven shell files. The seven
`# shellcheck disable=…` directives in the tree are load-bearing: removing one makes
shellcheck fail.

Destructive behaviour is exercised against a disposable virtual machine running a real
Immich, never against an installation holding real photos. The tool rewrites paths in
Immich's database; one command too many on a real instance damages real files.
