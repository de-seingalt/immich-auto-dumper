# immich-auto-dumper — technical documentation

This document describes how the tool works internally. For installation and daily use,
see the [README](../README.md).

## Design principles

- **No privileges.** Everything runs as the invoking user — never `sudo`. Docker access
  comes from `docker` group membership; files owned by the container's user are deleted
  *through* the container.
- **Immich is the source of truth.** The tool reads Immich's database to decide what to
  do and performs one narrow write (relocating an asset). It never "repairs" Immich: on
  any inconsistency it stops and asks the user to fix things on the Immich side.
- **Refuse rather than guess.** Every run starts with pre-flight checks (Docker access,
  DB schema, storage identity, path consistency, recent DB backup). Any failure aborts
  the run before the first destructive operation.
- **An unknown is never a negative.** A dependency that cannot be reached is reported as
  unverified, never as "nothing found" — see the diagnostic convention below.
- **Resumable and undoable.** Every step is journalled before it is taken, so a run
  interrupted at any point leaves each asset either fully archived or fully intact, and
  one identified run can be undone with `rollback`.

## Components

```
immich-auto-dumper.sh    entry point: CLI parsing, setup wizard, status, cron start/stop
lib/utils.sh             logging, locking, prereqs, storage marker, file identity, disk
lib/config.sh            config.conf parser and validator
lib/ui.sh                interactive prompts (whiptail with plain-text fallback), gauge
lib/detect.sh            auto-detection of containers, DB credentials, mounts
lib/db.sh                every SQL statement in the project (psql via docker exec)
lib/runlog.sh            the operations journal: records, states, retention
lib/archive.sh           the archiving engine, the reconciliation and the rollback
lib/backup_db.sh         DB-dump mirroring with retention
cron/crontab.example     cron template instantiated by `start`
config.conf              generated by setup; READ, never executed (git-ignored)
```

The entry point resolves itself through the `~/.local/bin` symlink (`readlink -f`) so
`lib/`, `config.conf` and `cron/` are always found in the real install directory.

## The diagnostic convention

Every function that can fail to reach something answers with three codes, not two:

| Code | Meaning |
|---|---|
| `0` | success, the result can be used |
| `1` | a legitimate negative — absent, empty, not covered |
| `2` | no conclusion possible — dependency unreachable, permission denied, timeout |

The distinction is load-bearing. "The database did not answer" and "the schema has
changed" must not produce the same message, and "the storage is unplugged" (an ordinary
state for a removable volume: the run ends quietly) must not produce the same decision as
"the mount is hanging" (a fault, reported, exit non-zero). A caller that collapses a `2`
into a `1` archives blind, or reports a broken install as healthy.

Two places absorb a `2` on purpose, and only those: the setup review
(`_config_check`) and the dry-run preview. Both must open and report against a mute
Immich — a user list that cannot be read costs the display, not the screen. **Nothing on
the archiving path absorbs a `2`.**

## config.conf is data, never code

`config.conf` is parsed by `lib/config.sh`, not `source`d. A line is a setting and a
value; the setting must be one the tool knows; the value must match what that setting is
allowed to hold; and nothing in the file is ever evaluated. Surrounding quotes are
stripped as punctuation, as is a leading UTF-8 byte-order mark; the only substitutions are
a leading `~/` or `$HOME/` in a path setting, rewritten as text.

This matters because the file is read by *every* command — including `status`, which
announces itself as read-only, including the uninstaller before its confirmation prompt,
and most often from cron, unattended.

Validation is per-setting: an absolute path for the path settings, a Docker container
name, a PostgreSQL identifier, a positive integer (with `ARCHIVE_MIN_FREE_MB` the one
number allowed to be zero, which disables the free-disk trigger). A folder in `USER_MAP`
may be neither absolute nor contain a `..` component, since it is pasted into
`${ARCHIVE_DEST_PATH%/}/<folder>/…`. Every fault is reported, by line number, rather than
only the first; a setting assigned twice keeps the later value with a warning.

The nine settings in `_CFG_ESSENTIAL_KEYS` identify this particular Immich install and
have no safe default, so their absence is a refusal at load: `CONFIG_LOADED` stays false
and every command but `setup` and `uninstall` exits rather than act on half a
configuration.

### The user mapping

One line per user, written by `setup` and editable by hand:

```
USER_MAP.<key>=<folder>
```

The key is the user's Immich `storageLabel`, or its UUID when the storage label is empty.
The value is a folder inside the external library. Two users must never be given the same
folder: their photos would collide on identical relative paths.

Configs written by earlier versions carry `declare -A USER_MAP` followed by
`USER_MAP["alice"]="Alice"` lines. Those are still read as data and normalised to the
form above; `setup` rewrites the file in the current format the next time it runs.

## Path model

Three coordinate systems describe the same file:

| Space | Example | Used by |
|---|---|---|
| Host, internal library | `/srv/immich/library/library/admin/2024/06/a.jpg` | `cp`, `du`, `stat` |
| Container / DB, internal | `/data/library/admin/2024/06/a.jpg` (`IMMICH_DB_LIBRARY_PREFIX`) | `asset.originalPath` before archiving |
| Container / DB, archive | `/external_library/Alice/2024/06/a.jpg` (`ARCHIVE_CONTAINER_PATH`) | `asset.originalPath` after archiving |

`lib/archive.sh` converts between them by prefix substitution
(`db_path_to_host_path`, `host_path_to_db_path`, `archive_build_dest_path`). The
destination preserves the full sub-path after the user folder, so any Immich storage
template layout survives unchanged. `USER_MAP` renames the per-user top-level folder on
the external storage.

`archive_build_dest_path` **refuses** (returns 1, echoes nothing) any source that is not
of the form `<upload location>/library/<user folder>/<rest>` with both parts non-empty.
The SQL selection no longer offers such an asset either — a double cover, because a
malformed destination path is the one shape Immich's library scan does not recognise.

### Why a stray slash matters

Immich stores its import paths with a trailing slash (`/external_library/Alice/`). A
folder taken from one and used as-is yields `Alice/`, which writes
`/external_library/Alice//2024/…` into `asset.originalPath` — while Immich's own library
scan records the single-slash form. The asset is then a duplicate at the next scan.
`_sanitize_folder` trims and collapses slashes wherever a folder enters the tool, and
`_config_check` reports a config that already carries one.

## Database access

All SQL goes through `_db_exec` (`lib/db.sh`), which runs `psql -t -A` inside the
Postgres container. Three details matter:

- **stdin is redirected from `/dev/null`.** `psql -c` never reads stdin, but
  `docker exec -i` keeps it open and drains it — and inside a `while read … done < <(…)`
  loop that stdin *is* the loop's input pipe, so docker would swallow the remaining rows.
- **The column separator is `\x01`**, not psql's default `|` under `-A`. A file path is
  free to contain a `|`: a directory named `we|ird` split into three fields, bash read a
  truncated parent directory and a size that was not a number, and that directory was
  silently never archived. The same separator is used for the Docker mount listing in
  `lib/detect.sh` and for parsed journal records (`RUNLOG_SEP`).
- **Three escaping layers** are applied depending on context: `_db_escape` (SQL string
  literals), `_db_escape_like` (LIKE wildcards), `_db_escape_regex` (POSIX regex
  metacharacters). The wildcard and regex helpers are applied *before* `_db_escape`.

A query result is never silently empty when the query could not run: `_db_exec` returns
`2`, and its callers propagate it.

### Schema validation

`db_check_schema` runs before any operation (via `check_prereqs`) and verifies against
`information_schema` that every column the tool relies on exists:

- `asset`: `id`, `originalPath`, `isOffline`, `isExternal`, `libraryId`, `deletedAt`,
  `ownerId`, `visibility`, `fileCreatedAt`
- `asset_exif`: `assetId`, `fileSizeInByte`
- `library`: `id`, `ownerId`, `importPaths`, `deletedAt`

One query per table, and each must actually run: a query that fails says nothing about
the schema, so it aborts the check with `2` instead of contributing an empty column list —
which would make every column look missing.

If an Immich upgrade renames or removes any of these, every run aborts at pre-flight with
an explicit error. The running Immich version (from the image's `IMMICH_SOURCE_REF`,
falling back to the compose tag `IMMICH_VERSION`) is logged at the start of each run so a
failure can be tied to the upgrade that introduced it. Limits to be aware of: the check
verifies column *presence*, so purely additive migrations or semantic changes with
unchanged names are not detected. After each Immich upgrade, run
`immich-auto-dumper test_run` before re-enabling the cron.

## File identity

Whenever the tool concludes that two files are "the same" it is about to delete one of
them, so the conclusion is earned by a **SHA-256 comparison**, never by size equality. A
foreign file that happened to match the source byte count was accepted as an already
archived copy, the database was pointed at it, and the original photo was deleted in its
favour.

- `file_fingerprint` echoes a digest or fails; it never echoes an empty digest, so a
  successful return can be trusted.
- `files_are_identical` answers `0`/`1`/`2`. The third code is the point: comparing two
  `stat` calls that had *both* failed read `0 == 0` and concluded "identical".
- `file_flush` pushes a freshly written file out of the page cache **before** it is
  verified and before any source is deleted. When `cp` returns, the data may only be in
  memory; a size check then reads that same cache, so the copy looks complete, the source
  is deleted, and a power cut in between leaves a truncated file and no original.

**Honest limit of the flush.** On a local disk, a USB drive or a mounted NAS, the file is
on the medium when `file_flush` returns. On a **write-back mount** (rclone
`--vfs-write-back`, async NFS) it is not: the upload may still be pending, and the
read-back that verifies the copy is served by the local VFS cache. There, "archived" means
"handed to the mount", and the tool relies on the mount to finish the job. Treat any
mtime read from such a storage as unreliable too — see the retention note below.

## Storage identity and availability

At setup, a marker file (`.immich-auto-dumper.id`, a random UUID also stored in
`config.conf` as `ARCHIVE_STORAGE_ID`) is written at the root of the external storage.
The marker makes the check agnostic to the storage type — local directory, OS mount,
FUSE/rclone, NFS, an intermittently-attached disk — because an inactive mount point is
just an empty local directory with no marker.

`_archive_dest_state` reads it, bounded by a 10 s `timeout` (a dead FUSE mount hangs on
read; timeout's own exit code 124 is what tells a hang from a missing file):

| Result | Code | Decision |
|---|---|---|
| Marker present, matching, and visible from the container | `0` | proceed |
| No marker at all — storage absent | `1` | run ends quietly, nothing written |
| Marker belongs to another volume | `1` | same: act on nothing |
| Read timed out, or marker present but unreadable | `2` | fault: refuse and report |
| Readable from the host but **not** from the Immich container | `2` | fault: refuse and report |

That last row is the one worth dwelling on. **The host seeing the storage is not Immich
seeing it.** In a real incident the host read the marker fine while the container answered
"Transport endpoint is not connected" — the mount had been replaced underneath the running
container. Nothing in Immich's configuration names or verifies a volume (a Docker bind
mount attaches a *path*, not a device), which is exactly why the marker exists, and why it
is read again from inside the container. The remedy is
`docker restart <server container>`, which the error message says.

Because the marker travels with the data, moving the storage to a new host path only
requires re-running `setup`.

## The operations journal (`lib/runlog.sh`)

Archiving one asset is four steps — copy, update the database, verify the result, delete
the source — and only the whole sequence is safe. So **each step is written down before it
is taken**, in one file per run under `$LOG_DIR/runs/`, with the run's outcome carried by
the file extension so it can never be half-written:

```
run-20260920T020000.active   in progress
run-20260920T020000.done     finished, everything completed
run-20260920T020000.failed   finished with entries left behind
```

An `.active` file found while a run holds the lock belongs to a run that was killed: a
dying process cannot rename its own file.

Records are JSON, one per line, written and read by this tool alone. A line that does not
parse makes its asset **untouchable** (state `illisible`) rather than guessed at: an
unreadable memo authorises nothing. Each record is flushed as it is written, with `sync -d`
on that one small local file and deliberately *without* `file_flush`'s fallback to a
global `sync` — losing a line costs traceability, not a photo, and a global sync on a busy
host would cost far more.

A path containing a line break would split one record across two lines and make the whole
file ambiguous; `runlog_path_is_recordable` refuses such an asset rather than invent an
encoding for a case that does not occur.

### States

| State | Meaning |
|---|---|
| `prevu` | decided, nothing done yet |
| `copie` | written at the far end, database not yet pointed at it |
| `base_a_jour` | database points at the far end, the other copy is still present |
| `source_supprimee` | finished |
| `annule` | finished, then undone by a rollback of this very run |
| `bloque` | gave up after `RUNLOG_MAX_ATTEMPTS` (5) tries — needs a person |
| `divergent` | Immich disagrees with the journal — needs a person |
| `abandonne` | the asset left Immich; nothing left to resume |
| `illisible` | the record could not be parsed; authorises nothing |

The first three are the resumable ones. `bloque` and `divergent` are what make a run exit
non-zero; `abandonne` does not — the asset left Immich, which is its owner's decision, not
a failure.

**The journal is a memo, never an authority.** Immich keeps living between runs, so the
database is re-read before every irreversible act and has to agree with what the journal
expects (`_archive_db_position`, which answers `source`, `destination`, `absent`,
`divergent` or `inconnu`). Immich remains the source of truth; the journal only remembers
what the tool was in the middle of doing.

Retention keeps the newest 30 `.done` files, ordered **by name** — the timestamp in the
name makes lexicographic order chronological. `.active` and `.failed` are never deleted
automatically: they represent work in abeyance, and deleting them would delete the problem
rather than the file.

## The archiving engine (`archive_run`)

### Pre-flight, in order

1. `check_prereqs` — Docker reachable as this user, `bc` and `sha256sum` present, the
   database answering, the schema valid. The database is asked *before* the schema, so a
   container that merely needs starting is not reported as a schema change.
2. `check_archive_dest_ready` — the storage marker (see above). `1` ends the run quietly,
   `2` exits non-zero.
3. `guard_path_consistency` — see below; on inconsistency the cron is disabled.
4. `acquire_lock` — see below.
5. Boundary check — `TARGET` (and `MAX` for unforced runs) must be configured.
6. **The gate** — see below.

### Decide first, act afterwards

Measuring the library and reading the thresholds writes nothing, so the whole decision is
taken before anything irreversible can happen. That split is what lets **one** gate stand
in front of every act that touches a photo or a database row.

Normal (unforced) runs trigger on **either** of two independent conditions: the
**measured size of `UPLOAD_LOCATION/library`** (`du -sb`, apparent size) exceeds
`ARCHIVE_LIBRARY_MAX_MB`, or the **total free disk space** on that filesystem drops below
`ARCHIVE_MIN_FREE_MB` (0 = disabled). The second condition exists because the first
assumes the library is the only thing that can fill the disk — on a shared filesystem,
unrelated data (Postgres, Docker, logs…) can fill it instead, in which case the
library-size trigger would never fire on its own. `--force` bypasses both. All paths bring
the library down to `TARGET`, never below.

Boundaries are stored in MiB (1 GiB = 1024 MiB) so fractional-GB limits are expressible;
the deprecated `*_GB` keys are still honoured for older configs.

### The gate: a recent, usable dump

Archiving rewrites `originalPath` rows, so a **database dump younger than 7 days** in
`UPLOAD_LOCATION/backups/` is what makes those rewrites recoverable. It is demanded
**once**, in front of both a fresh archive and the resumption of an earlier run — the
resumption drives the very same pipeline (copy, UPDATE, adopt, delete the source), so
exempting it would be exempting the thing the check exists to protect.

Two details of `_recent_usable_dump`:

- It demands a **non-hidden file larger than 1 KiB**. The previous test was "any file
  here, modified in the last 7 days", and the file that satisfied it was Immich's own
  13-byte `.immich` marker, while the last real dump was two months old and predated a
  major-version upgrade.
- It matches on **size and age, not on a name pattern**. A name filter would tie the tool
  to a convention of Immich's that is free to change — exactly the coupling that breaks at
  the next upgrade.

The gate only fires when there is something to do, so an install whose Immich backup job
is broken does not log an error every night it had nothing to archive. Waiting for a dump
loses nothing: every state an entry can be parked in holds both a file and a row that
point at each other. A dry run is exempt, since it writes nothing.

### Reconciliation

`archive_reconcile` is phase one of every real run: it picks up what earlier runs left
unfinished, before the thresholds are acted on, because a half-archived asset is a
liability whether or not the library is over its limit today. It is deliberately not a
reason to refuse a fresh archive either — the moment the disk is filling up is exactly
when the tool has to keep working.

Each old run file is appended to in place and then renamed, so one run's history stays in
one file. What remains unfinished afterwards fills `ARCHIVE_IN_FLIGHT`, and the candidate
selection **leaves those assets alone**: an asset that keeps failing is still an internal
asset, so a fresh run would pick it up again and open a *second* entry whose attempt
counter starts at one — which is how an asset blocked by a foreign file at its destination
collected four "first attempts" across four runs and never reached the ceiling meant to
park it. `annule` is not held: a rollback put that asset back in the library, so it is an
ordinary candidate again.

### Candidate selection

`db_get_archive_candidates` groups active assets (`deletedAt IS NULL`, not offline, not
already external, path under `IMMICH_DB_LIBRARY_PREFIX`) by their **immediate parent
directory** and orders groups by the oldest `fileCreatedAt` they contain. This makes the
unit of work template-agnostic: the genuinely oldest photos leave first, and a directory is
never left half-archived — the stopping condition is only evaluated *between* directories.

The candidate list is **captured, checked, then iterated** — never iterated as a process
substitution. `while … done < <(db_get_archive_candidates)` discards the function's exit
code: a database that stopped answering after pre-flight would read as no rows, i.e. as
"nothing left to archive", and the run would report `Archive complete. Freed: 0 B.` with
`rc=0`, every night. The same treatment is applied to the per-directory query, where a
failure costs one directory and is counted (`dirs_failed`) rather than announced as
archived.

### Per-asset pipeline (`_archive_process_asset`)

Each transition is recorded **before** the act it describes, and a record that cannot be
written stops that act.

1. **→ `prevu`.** Record, then ask what is already at the destination
   (`_refuse_if_occupied`): nothing (write it), the identical file (skip the copy, update
   the database only), or a *different* file — which skips the asset and keeps the source.
   Two users mapped to the same folder in `USER_MAP` is the usual cause.
2. **Copy + verify → `copie`.** `cp -p` (which keeps the timestamps: without `-p` every
   archived photo arrives dated the day it was archived, losing the only file-level trace
   of when it was taken), then flush, read back, and compare against the fingerprint taken
   before anything moved. A partial file is removed, on whichever side it was written; the
   other copy is still in place, so nothing is lost.
3. **DB update + adoption → `base_a_jour`.** One `UPDATE` rewrites `originalPath` and
   *adopts* the asset into the external library whose `importPaths` covers the new path and
   whose owner matches the asset's owner (`libraryId` set, `isExternal = true`,
   `isOffline = false`). Adoption is what prevents Immich's periodic library scan from
   re-importing the file as a duplicate, and it also takes the asset out of reach of the
   storage-template migration job. Two conditions are then checked, and either undoes the
   update: an external library must cover the destination, and the copy must be visible
   from inside the container (`test -f`). Dry runs surface the first case as a warning
   (`db_asset_would_be_external`).
4. **Source deletion → `source_supprimee`.** Through the container, which owns the library
   files, and only if the source still carries the fingerprint recorded before the copy.
   This is the **one** record written *after* its act, so its failure is only a warning:
   the next run re-reads the database, finds the asset at its destination and finishes.

**When the restore fails, the copy is KEPT.** If a fault at step 3 cannot be undone —
`_archive_restore_db` could not point the database back at the source — the copy stays,
because the database points at it and the asset therefore still has a file behind it. This
is the single most important asymmetry in the engine: removing the copy is what turned a
recoverable failure into an asset with no file *and* an unreferenced original. The entry is
recorded `divergent` and the log names the `rollback` command.

**Accounting comes from the filesystem, not from Immich.** What a move frees is read with
`stat` on the source while it is still there. Immich's own `fileSizeInByte` is only good
enough to *sort* the candidates: with the exif rows missing, those sizes summed to zero,
the stopping condition was never met, and a run asked to free 178 KB moved 1.2 MB — every
directory there was. For the same reason the stopping condition **re-measures** the library
(`du`) between directories rather than adding up what the metadata advertised.

### Sidecars

XMP/JSON sidecars are moved alongside their asset and are **not tracked in Immich's
database at all** — verified against v3.2.0: no `%sidecar%` column in any table, and
`asset_file` carries only `preview`/`thumbnail`. Immich finds them by naming convention
when it scans. That is why the tool has to move them itself, and why the journal cannot
describe them.

`_sidecar_candidates` derives the four possible names — `<path>.xmp`, `<path>.json`, and
the same two with the extension stripped from the **file name** (not from the whole path)
— and deduplicates them, since for an asset with no extension the two forms name the same
file. Both directions use that one helper, so what goes out and what comes back are
decided in one place. A sidecar is held to the same fingerprint discipline as its asset.

On the way back they are re-derived from the destination path. No fingerprint was recorded
for them at archive time, so the check proves the transfer intact, not that the sidecar was
never edited on the storage since — that is all the journal allows, and it is strictly
better than abandoning it.

### Exit code

`archive_run` returns non-zero when the run was refused, when a directory could not be
read, or when it put at least one entry into `bloque` or `divergent`. That count is of
entries **written during this run**, not of entries present in `runs/`: counting what is
present would leave the light red night after night, since a divergent entry survives
until an operator deletes the run file. Counted this way, the non-zero exit falls exactly
once, on the run that produced the problem.

## Rollback (`archive_rollback <run-id>`)

Explicit, never automatic: bringing files back is a decision, taken on one identified run,
whose id `status` prints. It requires the storage to be reachable and takes the same lock.

Every entry that reached `source_supprimee` is walked backwards: copy in (through the
container, which owns the library), verify, point the database at the source, remove the
external copy, bring the sidecars back. The same guards apply in both directions — the
shared primitives `_transfer_and_verify` and `_refuse_if_occupied` are what hold the way
back to the same discipline as the way out. Archiving had the occupied-path guard and the
rollback did not: it wrote over the library path with `cat >` without looking at what was
there.

An asset is **refused, and reported**, when its current state does not match what the
journal says it should be — Immich no longer points at the recorded destination, or the
archived copy's fingerprint has changed. A refusal touches nothing, so it is logged and not
journalled: writing it into the journal would leave `status` reporting a decision as
pending for ever. `archive_rollback` returns non-zero if it refused anything, so a partly
accepted rollback can be re-run once the cause is dealt with.

**The `annule` state is what stops a rollback being replayed.** Each undone entry is
recorded `annule` in the *original* run's journal. Without it, the only question asked was
"does the database point at the recorded destination?", which cannot tell this run's work
from a *later* run that archived the same asset to the same path: replaying rollback A
after run B had re-archived those assets undid B's work instead, left B's journal claiming
a job that no longer existed, and could be repeated indefinitely.

Writing into the original run's journal does not falsify that run's account of what it did;
it extends it with what happened afterwards.

## Locking

Two runs must never overlap: they rewrite the same rows and copy to the same destination.
The lock is a **directory**, created with `mkdir` — the kernel either creates it or fails,
with nothing in between, and it does not follow a symlink planted at the path. The
previous lock tested for a file and *then* created it, and that gap was wide enough that
two simultaneous forced dumps both started, once in five attempts.

- It lives beside the logs, **not** under `$XDG_RUNTIME_DIR`: cron runs have no runtime
  dir, so keying the path on it gave the nightly run and a manual one two different locks —
  no mutual exclusion in exactly the case that matters.
- It records the holder's PID **and boot id**. A lock directory on persistent storage
  survives a reboot, after which that PID may well be alive again as an unrelated process,
  jamming every subsequent run with a bogus "already running".
- An orphaned lock is claimed by **renaming it aside**, then deleting the renamed copy:
  `rename()` succeeds for exactly one process, so a loser can never delete the fresh lock
  the winner just created — which a plain `rm -rf` would let it do.
- An absent PID file is given one second to appear before the lock is called orphaned,
  since the holder writes it just after `mkdir`.
- `release_lock` only removes a lock this process holds, and is idempotent, so the explicit
  call and the `EXIT`/`INT`/`TERM` traps can all run.

`lock_state` is read-only, for `status` and `stop`, which must report on the lock without
ever taking it.

## Path-consistency guard (read-only)

`db_check_path_consistency` detects that Immich's view diverged from the config:

- the internal library prefix derived from a live asset no longer matches
  `IMMICH_DB_LIBRARY_PREFIX`, or
- archived assets under `ARCHIVE_CONTAINER_PATH` are reported **offline** while the
  storage is reachable — the external library path was likely changed in Immich.

The offline count is split into live and trashed, and **both halves count**. Immich marks
an asset offline and moves it to the trash in the *same* operation, so counting only the
live ones made the check blind exactly when it mattered: the same three assets read
`INCONSISTENT` and then, moments later, `OK`. When trashed assets are among them the report
says out loud not to empty the trash before the path is fixed. The feared false positive —
someone deleting archived photos on purpose — is ruled out by `isOffline = true`: a
deliberately deleted asset is not offline. It is the conjunction that signals the failure,
and nothing needs remembering between runs.

The signal is only trustworthy while the external storage is reachable (with the files
genuinely absent, every archived asset reads as offline), so every caller gates on
`check_archive_dest_ready` first.

On inconsistency the run aborts and the cron entries are commented out (`disable_cron`), so
a stale configuration cannot keep acting. On a `2` — unverified — the run is refused
without touching the cron. The tool never rewrites the database to reconcile the two: the
user fixes the path in Immich and re-runs `setup`.

## Setup on an existing config (the review path)

`setup` is the only writer of `config.conf`, and it is expected to be re-run — after an
update, or just to check where things stand. Walking the full questionnaire every time
pushes the user to re-answer questions they cannot remember, on a tool that rewrites paths
in Immich's database; so with a config already present, `_setup` opens on `_setup_review`
instead: saved settings (`_config_summary`), verdict (`_config_check`), then a three-way
choice between keeping the config, reconfiguring step by step, and quitting. The
step-by-step is only *recommended* — first in the menu — when a check actually failed.

The review runs **before** `detect_docker_cmd`, which exits when the daemon is
unreachable: showing a saved config and managing the schedule must keep working while
Immich or Docker is down. Every live check in `_config_check` is therefore guarded by
`probe_docker_cmd` / `_db_reachable` and degrades to a note. Findings land in three
buckets, and the distinction is the whole point of the screen:

| Bucket | Meaning | Effect |
|---|---|---|
| `CFG_PROBLEMS` | a setting no longer holds (loader refusal, missing key, `TARGET ≥ MAX`, invalid `BACKUP_RETENTION`, empty `USER_MAP`, a stray slash or two users in one folder, container gone, Immich user with no folder, path drift, destination path absent) | reconfiguration recommended |
| `CFG_OUTDATED` | keys in `_CFG_BACKFILL_KEYS` absent from the file — a config written by an older version | offered for append-only backfill |
| `CFG_NOTES` | live state, not a config error (storage currently unmounted, Docker or the DB unreachable, legacy `USER_MAP` form, Immich keeping more dumps than we mirror) | informational |

Whatever `config_load` refused is replayed here from `CFG_LOAD_PROBLEMS`: the log alone is
not where someone running `setup` looks.

`_config_has_key` greps `config.conf` rather than testing the variable: a variable can be
set from the environment or defaulted elsewhere in the script, which would hide a key that
is genuinely absent from the file. `_config_backfill` only ever *appends* lines — through a
temporary copy and a rename, like every write to this file — so a value the user edited by
hand is never rewritten, and it logs each line it wrote, because a value that appears in a
file on its own is a value nobody chose.

`_user_map_count` exists because a config carrying `declare -A USER_MAP` with no
assignment leaves the array declared but **unset**, and `${#USER_MAP[@]}` on an unset array
aborts under `set -u` — which is exactly the config that needs reporting on.

### Boundaries and the disk ceiling

The wizard validates `MAX` against a hard ceiling: **free disk + the library's current
size**, the most the library can ever reach before the disk itself fills. Past that the
disk fills before `MAX` is reached and archiving never fires. `status` re-checks the same
ceiling, because unrelated data erodes it over time, and says whether the free-disk safety
net is there to catch it.

`_recommended_min_free_mb` is 10% of the disk, clamped between 2 and 20 GiB and rounded
down to a whole GiB. Two deliberate details: a disk size that cannot be read falls back to
the 2 GiB floor and **never to 0** (zero is a perfectly good value when the *user* picks
it — it turns the trigger off — but a default choosing it for them disables the safety net
while presenting it as the recommendation); and the whole-GiB rounding round-trips exactly
through `mb_to_input`, whose two-decimal rendering would otherwise lose a few MiB and make
simply accepting the pre-filled default look "below the recommended floor".

## DB-dump mirroring (`backup_db_run`)

Copies every non-hidden file from `UPLOAD_LOCATION/backups/` to
`<storage>/.immich-backup/`, then applies retention (`BACKUP_RETENTION` newest kept). It
takes the lock, and it intentionally skips the consistency guard: mirroring dumps stays
safe and useful even while a path change is being resolved. It never touches the database.

`BACKUP_RETENTION` is validated **before anything is copied**, and an unusable value
refuses the whole run — including the dry run, which would otherwise report on a policy it
cannot apply. An empty or zero value deleted every dump on the external storage and logged
it at INFO, which a cron mail reads as a success; a non-numeric one crashed mid-rotation.
No default stands in for it: an invalid retention means the configuration needs fixing.

A dump already present at the destination with the same size is left alone, so each run
transfers only what is new rather than the whole retention window. This is deliberately a
size comparison and not a fingerprint, unlike everywhere else the tool decides two files
are the same: nothing is deleted on the strength of this answer — at worst a dump is
re-copied — and a fingerprint would mean reading the entire retention window back from the
remote every single run. What a fingerprint *does* guard is the copy this run makes, and
that one is flushed and verified right after it is written. A destination of a *different*
size is a truncated leftover (interrupted run, cancelled upload) and is overwritten.

A dump that has vanished between the listing and the `stat` — Immich rotates its own dumps
— is **skipped**, not counted as zero: a size of 0 would never match the destination and
the dump would be re-copied for ever.

**Retention orders by filename, never by mtime.** Dump names start with a timestamp
(`immich-db-backup-YYYYMMDDTHHMMSS-…`), so lexicographic order is chronological — and
unlike mtime, a name cannot be misreported by the storage. This is not a stylistic choice:
on a write-back mount a file whose upload is still pending has no known modification time
and the mount answers with a placeholder date far in the past. Rotation by mtime then ranks
the dumps it has just copied as the oldest on the volume and deletes them, cancelling their
upload in flight — silently, while the log still reports every file as copied. The journal
retention in `lib/runlog.sh` follows the same discipline for the same reason.

## Scheduling

`start` instantiates `cron/crontab.example` into the user's crontab (via the
`~/.local/bin` symlink so paths survive updates, and with an absolute path because cron has
a minimal PATH): `dump_now` daily at 02:00, `sync_now` weekly on Sunday at 03:00, both
appending to `cron.log`. `stop` comments the entries out and waits up to 60 s for a running
operation to release the lock. The path-consistency guard may also disable the entries
autonomously.

`cron_state` reports three distinct states, and every caller (setup, `status`) branches on
them rather than on a boolean: `active` (a live schedule line), `disabled` (schedule lines
present but commented out — what `stop` leaves behind, and what `start` re-enables before
appending anything), `absent` (nothing scheduled at all). The middle state is the reason
`start` un-comments first: a commented line still matches the substring check that decides
whether an entry is missing, so without that step `start` after `stop` would no-op.

A **schedule line** means one whose payload begins with a digit, `*` or `@`, and all four
cron-touching functions agree on that definition: `cron_state`, `cron_entries`, `start`'s
un-comment step, and `disable_cron`. A line that merely mentions the tool — a `MAILTO=` or
a `PATH=` naming its path, a user's own comment — is therefore never read as a job, turned
into one, or commented out. `disable_cron` used to match the substring alone, which made
`stop` comment out such a line while `start` could not restore it (its un-comment pattern
requires the schedule payload), leaving it disabled for good.

## Dry runs

`--dry-run` (and `test_run`, which implies `--dry-run --force`) suppresses every
destructive operation. Two rules hold it honest:

- **A dry run opens no journal and writes no record.** A simulation must leave nothing
  that a later read takes for work done.
- **No line a dry run logs may read as work done.** `status` reports the last
  `Archive complete` and `DB backup:` lines as history, so every simulated line carries the
  `DRY-RUN:` prefix and different wording. Its closing line says "would free", not
  "Freed".

A dry run still reports the outstanding work it *would* resume (from `runlog_summary`), and
still sums what it would free so that its stopping condition matches a real run's — a
simulation that always announced every candidate directory, where a real run stops after
two, is not a preview.

## Logging

`_log` writes to stdout/stderr (coloured on a TTY) and appends to
`$LOG_DIR/immich-auto-dumper.log` (default `~/.local/state/immich-auto-dumper/`, honouring
`$XDG_STATE_HOME`), truncated to `LOG_MAX_LINES`. A log directory that cannot be written
skips file logging rather than aborting the run.

## Interactive layer (`lib/ui.sh`)

Two backends: `whiptail` when it is installed *and* stdout is a terminal for it to draw
into, coloured plain text otherwise. Every prompt leaves its result in the global
`UI_VALUE` and returns 0 for confirmed, 1 for cancelled, so a cancel is not swallowed by a
command-substitution subshell.

**Dialog geometry is computed from the rows whiptail actually draws.** `_wt_geometry`
counts *wrapped* lines, not logical ones: a body of 8 logical lines that wraps to 11 given
a box sized for 8 has its end cut off — and because the computed height stays under the
terminal cap, `_UI_CLIPPED` stays 0 and `--scrolltext` is not added either, so both safety
nets fail together and silently. It wraps on words as whiptail does, normalises a literal
`\n` to a real one (whiptail renders both as breaks), and measures characters rather than
bytes so accents and the `▼`/`▲` markers count correctly. The terminal height is asked of
the terminal itself — `$LINES` is set by *interactive* shells only, and is empty inside a
script.

A body taller than the terminal is made scrollable rather than clipped, which matters most
on the review screen: the thing being hidden would be the list of blocking problems the
screen exists to show.

## Auto-detection (`lib/detect.sh`)

Every value the tool needs is already defined by the running Immich install, so the wizard
reads that ground truth via `docker inspect` and the database, and asks the user only to
confirm or to choose between real alternatives.

The Docker mount mode (`:ro`) is **deliberately not** used as a filter. `:ro` restricts the
*container* — so the Immich app cannot write to an external library, which is often set on
purpose — but this tool writes through the *host* filesystem, not through Docker. Whether
it can write there is a host-side question, answered when the storage marker is written
during setup.

The upload mount is found in three passes: the mount whose container path is the parent of
the DB library prefix, then the canonical destinations (`/data` on current images,
`/usr/src/app/upload` on older ones), then any bind mount whose host side actually holds a
`library/` folder.

Container detection matches on name patterns and the **first match wins**, but it is not
silent: on a host running two Postgres containers (two projects side by side is ordinary)
the wizard names every candidate and says which way the choice went, so a wrong guess is
visible there rather than discovered later against the wrong database.

## Failure-mode summary

| Event | Behaviour |
|---|---|
| Storage unplugged / mount down | Run ends quietly (`1`), nothing written, resumes next time |
| Wrong disk mounted at the path | Run ends quietly (`1`): the destination is not the one configured |
| Mount hangs, or marker unreadable | Run refused, exit non-zero (`2`) |
| Storage visible to the host but not to the container | Run refused, exit non-zero; restart the server container |
| Partial copy (disk full, I/O error) | Fingerprint mismatch: copy removed, asset skipped, source intact |
| Destination occupied by a different file | Asset skipped, source kept (usually two users in one `USER_MAP` folder) |
| No external library covers a destination | DB update undone, asset skipped, warning in dry run |
| DB update succeeds but cannot be undone | Copy **kept**, entry `divergent`, exit non-zero, `rollback` offered |
| Journal cannot be opened or written | Run refused before anything is touched |
| Journal record unreadable | That asset is left untouched (`illisible`), never guessed at |
| Immich schema changed by an upgrade | Every run aborts at pre-flight with the missing columns listed |
| Database stops answering mid-run | Run aborts non-zero; never reported as "nothing to archive" |
| External library path changed in Immich | Run aborts, cron disabled until re-setup |
| No recent DB backup (< 7 days) | Archiving *and* resumption both refuse to start |
| Asset deleted in Immich mid-flight | Entry `abandonne`; the run does not fail on it |
| Asset moved elsewhere in Immich | Entry `divergent`, untouched, exit non-zero |
| Storage reports unreliable mtimes (write-back mount) | No effect: names and sizes decide, never mtime |
| Concurrent invocation | Second run exits on the directory lock |
| Reboot with a lock left behind | Boot id mismatch: the lock is recognised as stale |
| Crash mid-run | Lock released by trap or detected stale; the journal resumes each asset where it was left |

## Tests

The pure-function test suite is not shipped with the tool: an end user has no use for it,
and it lives outside the repository. There is no CI. `shellcheck -S warning -x` is expected
to be clean on all eleven shell files.
